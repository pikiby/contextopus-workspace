# Workspace 1.6.0: coordinate concurrent card edits

Multiple sessions can read the same context while reserving different cards for
editing. A reservation records the owning work cycle, a short edit reason and an
expiry time. A competing writer receives that information instead of overwriting
the card or taking part of a related set.

## Changes

- Reserve related existing cards atomically with `workspace.reserve`.
- Inspect, renew or release ownership through `workspace.reservations`,
  `workspace.reservation_renew` and `workspace.reservation_release`.
- Proposal preparation covers the complete affected set, including incoming links.
  Application checks both current revisions and the exact live reservation.
- Successful saves release their cards. Expiry frees abandoned reservations;
  the old proposal must be read and prepared again, even if its cycle reserves again.
- Internal card updates, renames, deletion and format migration respect ownership.
- The agent procedure asks for a concrete edit reason before preparing changes.

## Update and compatibility

This is an independent Workspace module release for **Core >=1.5,<2**. Core and
Session Search do not need a release for this feature. The normal module update
adds Workspace SQL schema 2; Markdown format remains 5. Existing knowledge,
settings, Git history and pending proposals are preserved. Reviewed pre-upgrade
proposals acquire ownership on application after the existing conflict checks.

Use the normal module lifecycle with a coherent backup. Do not replace package
files while the module is running or downgrade a schema-2 database with the old
binary. See [installation](../install.md) and [concurrent editing](../concurrent-editing.md).

## Boundaries

Reading and search remain available. Reservations default to 15 minutes and may
be renewed while active. Independent sessions use independent cycles; an explicit
handoff may keep a cycle. Cycle IDs are not authentication credentials. Direct
Markdown editors remain possible and are protected only by observed revision
conflicts. New cards with different IDs can still duplicate a topic: agents must
compare their meaning. No Git branches, agent chat or automatic semantic merging
are introduced.
