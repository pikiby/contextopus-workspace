# PCW v3 implementation contracts

Historical format-1 contracts; format-2 changes are in [v4 contracts](context-workspace-v4-contracts.md). Plugin **0.12.2** and workspace format **1** are independent versions. Updated sources do not imply an updated installed MCP.

## MCP interface and opening

Only `pcw_query` (read) and `pcw_execute` (mutation) are published, with `operation`, `work_root`, `workspace` and `arguments`. Operation parameters, including `cycle_id`, are inside `arguments`; coordinates are outside. All 42 former operations remain behind an explicit read/mutation allowlist. `describe` with an operation returns its entry point and JSON schema; without arguments it returns operation names. It requires no workspace, storage or journal. Schemas derive from live runtime signatures; missing, extra and wrongly typed values fail before opening storage. Arbitrary runtime methods remain inaccessible. The common dispatcher preserves authority, revision and approval checks, logging concrete operation names. Clients must refresh tools/list after upgrading from individual tools.

`workspace_create` accepts `request_id`, approved full `instructions_content`, `project_content` and `user_request`, with all five explicit YAML settings. Identical retries resume; a different request never replaces existing storage. Creation starts neither a cycle nor a task. `workspace_inspect` checks without migration. `startup` accepts request/purpose/restart plus `invocation` and `task_id`; an existing supported workspace is required. Purposes: work, instructions, audit, rework. Implicit invocation is allowed only for work when instructions permit it. MCP arguments do not authenticate human message origin.

Search, read/read_many/list, instructions, PROJECT, Current and history reads need no cycle. Selected bodies are read completely. Reading creates no workspace and repairs no index; stale rows are excluded and marked pending. Locks and observation logs are service effects of reading.

## Compatibility and resumable migration

`format.json` lives under `.pcw/.control/<workspace>/`. Recognized unnumbered legacy storage has knowledge, user instructions and a known index configuration. Unknown layouts/future formats block opening. Transition 0→1 adds an absent PROJECT without invented goals, empty current directory, updates derived index if needed, and marks the format after verification. Old Current remains byte-preserved.

`upgrade_plan` returns compatibility, changes, source revision, `pending_work`, `blockers` and `ready`. Pending work includes request/task IDs, temporary titles, proposal topics/states; an open record does not prove a running agent. Revision covers knowledge, tmp, index pointer and control state, so changed drafts/cycles require a new plan. Even current formats are checked. `project_description` distinguishes missing/empty/placeholder/present; `content_reviewed:false` means content was not assessed. Presence is no proof of completeness. Apply, repeat and already-current responses also return this state. Report incomplete PROJECT explicitly; fill it only when requested, through normal project_update/apply and current approval rules.

`upgrade_apply(expected_revision,user_request)` repeats checks under lock. Compatible active cycles retain IDs, drafts, revisions and states; migration neither applies proposals nor finishes work. Unknown states, interrupted starting/closing/restarting and damaged proposals are blockers requiring separate recovery, not cancellation of all cycles.

`control/backups/<id>/` contains complete workspace (tmp/index included) and control (cycles and ID reservations included), excluding locks, the current receipt and old backups. Hash-check snapshot files, source bodies, temporary data and cycle states before marking format. Derived index may change; remaining preparation is returned separately. `migration.json` persists the operation. Unfinished plans expose `resume_revision` and snapshot path: retry uses those originals without overwriting saved files. Source conflicts or corrupt snapshots stop continuation. Old unfinished migrations lacking the snapshot layout need separate examination. Batch traversal is limited to user-selected lists/directories. Semantic knowledge/rule changes are not technical migration.

## PROJECT, Current, settings and materials

`project_update` prepares a proposal against cycle/content/revision/user request; `project_apply` writes the displayed revision under current knowledge approval. Instruction edits retain their own mandatory-approval prepare/apply. `current_create` creates task UUID and cycle binding with idempotent request ID. Per-task `current/<task-id>.md` stores goal, constraints, verified_state, next_step, blockers and status (active/blocked/completed/cancelled). Updates require the read whole-file revision and cycle binding. Startup can continue task_id; tmp cleanup preserves Current, and PROJECT edits do not rewrite tasks.

Settings come only from instruction YAML; semantic rules remain free text. Missing old values are `allow_implicit_updates=false`, `knowledge_approval_required=true`, `git_history_enabled=false`, `material_max_tokens=null`, `create_required_sources=false`. New-context standard choices are false/false/true/1024/false respectively. Offer the complete standard set first, then ask only unchosen settings. For the token limit, first offer recommended  1024, another number or null; ask for a number only if “another” lacked one. A UI preselection is not the user's answer. All five creation values are explicit; accepting the displayed set or specifically answering required-source creation establishes that choice, while generic write permission does not. Reject duplicates/invalid types and never silently update existing rules.

`proposal_prepare` retains create/update/move/delete/merge/split and adds description. Reads return title, description, labelled link_targets and exact links; optional from_id verifies a real outgoing link. Labels need no extra model call. Enabled limits measure every final body with the index tokenizer. `needs_split` returns IDs/keys, actual counts and limit without creating an applicable proposal or writing knowledge. The agent chooses semantic boundaries; embedding windows remain512/64. Metadata-only edits do not re-embed bodies.

## Git and observation boundaries

History snapshots knowledge/instructions/PROJECT initially and after apply. Under lock, control/history saves exact texts and file sets, then Git builds through a separate index and local commit. Retry never reads later foreign files; queue order is preserved; identical trees create no commit. Tmp, Current, vectors and analytics are excluded. Operations: history_list (ID/path/message/date filters), history_search (exact additions/deletions), history_changes (commit contents and declared lineage), history_diff/read/retry. List/text responses are bounded and paginated. Proposal summary and merge/split/replace transformations participate in its revision and Git trailers. Source/result IDs establish declared lineage; similarity does not. Old commits gain no invented lineage. Write/index and Git outcomes are separate; pending Git does not mean saved knowledge was lost. Historical restoration uses an ordinary proposal under current rules; no remote push occurs.

Workspace dispatch writes parameters/results without permanent Markdown copies, errors, duration, actual response bytes and Git references to `core/analytics/events.sqlite`. events/blobs store events; event_references store verified links. instructions_revision/ref, runtime_version and procedures_revision identify rules/code/procedures at the call. Observing a version is not proof the model read it. Core operations.sqlite3 has separate anonymized metrics; do not sum both logs as independent calls.

No full before/after context snapshot is made for each call. Match returned text to exact Git file versions, retaining ID/owner/commit/blob/hash/extraction method. A mismatch is unversioned, never silently HEAD. With Git off, SQLite creates no second version archive. There is no atomic file/Git/SQLite transaction; started without completion means unknown outcome.

`analytics_query` defaults to the selected context and last seven days; explicit workspace/task/cycle/import/tool/date/instruction/runtime/procedure filters narrow scope. Cursor fixes filters and insertion upper bound; UTC since is inclusive and until exclusive. analytics_report returns exact scope totals plus labelled paginated counts/groups with event/metadata-byte limits; unknown dates and missing evidence remain explicit. analytics_read bounds bodies/references; analytics_reference_read retrieves verified Git versions (reference_index=-1 means then-current instructions); analytics_blob_read pages old/imported bodies. Historical rules assess historical actions but grant no current authority. Procedure fingerprints reveal change without reconstructing text: a matching source/release is needed.

Old versions/observed/blobs remain until verified conversion. analytics_migrate defaults to a bounded plan; apply converts only source-hash-and-redacted-text matches into Git links and deletes only unused blobs. Unknown versions and old parameter/result/error bodies stay. history_index restores bounded commit/lineage metadata pages; new commits index separately. history_lineage walks record versions preserving merge/split/replace groups, with date filtering before limits. Unverified declarations add no confirmed edges. Git reconstructs the index, not missing read/error events.

analytics_evaluate stores a separate assessment with criteria, evidence IDs, scope and instruction basis, validating events/revisions against the log. Unknown rules stay unknown. Bytes/duration do not establish tokens or cost. Analytics-read responses are not recursively copied. analytics_import accepts an explicitly selected codex-jsonl or pcw-session-v1 file, retaining public messages/calls and source coordinates while excluding system/developer/analysis. Time coincidence proves neither MCP linkage nor authorship. Redaction precedes storage but cannot reliably detect arbitrary unlabelled secrets.

## Audit, required sources and analysis

Audit returns observable format faults, duplicate IDs/bodies and missing link targets, with excerpts/revisions, without changing durable memory/index. The agent performs semantic review and labels hypotheses. Rework uses ordinary proposals; “all” requires enumerating the complete scope rather than one top-N search. test_workspace_v3, test_history_v3, test_analytics_v3 and regression tests cover contracts; real stdio checks MCP. Real-agent/model results remain separate and never prove universal compliance.

A body may contain YAML `required_sources` entries with `url` and bounded `extract` questions. This is body content, not frontmatter or navigation IDs. Normal prepare/write/read preserve it without extra operations. The agent freshly checks every source whenever receiving the material, including repeated reads and disabled create_required_sources; it extracts the requested answer with conditions/check time, labels unavailable sources, and does not pass old answers off as fresh. Instructions define creation criteria; the required-sources reference defines reading. Runtime neither fetches pages nor verifies agent compliance.

The short w-analyze entry loads the canonical analyze MCP procedure using analytics query/read/blob, optional history list/diff and explicitly selected other-agent history. Bound context/task/cycle/period and capture an upper time bound before paging the entire scope. Separate observed reads, from_id traversals, edits and errors from inferred knowledge use. Missing host history is not proof of omission; unbound calls cannot be assigned to an agent by time alone. Report in chat; save assessments separately only when requested. No automatic benchmark or token savings inferred from response size/time.
