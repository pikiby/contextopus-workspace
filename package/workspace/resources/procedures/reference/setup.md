# Runtime setup and recovery

Use this reference for actual tool or embedding failures. Resolve the workspace under [Context selection](procedure:workspace); setup does not authorize creation or switching. Independent reading requires no startup. Work startup follows the selected workspace's invocation setting, uses a fresh request_id and returns instructions, project and bounded state. Retry with the same ID. Missing storage requires create or recovery as appropriate; incompatible format requires upgrade, never hidden migration. A new conversation is not a reason for diagnostics. Availability does not prove cached weights or working embeddings.

When diagnostics or repair are needed, the primary reuses existing authority and established observations and performs bounded Contextopus setup work itself. Ask only for authority that is actually missing. Setup does not discover agent models, reasoning capabilities or tool maps, and does not by itself assign a worker the full Contextopus cycle. A missing interpreter or distribution does not require broad source research or web diagnosis.

An exposed server with a broken workspace returns `recovery_required`. A small storage marker outside the derived index distinguishes missing storage from a new workspace. The cycle agent calls `recover_workspace` with the cycle_id returned by startup. Missing knowledge remains blocked; this tool does not recreate it. Retry the original startup request after recovery. A designated clean-context agent may perform the entire cycle; an ordinary diagnostic worker is not assigned permanent-memory management.

## Check the installed service

Contextopus advertises `guide`, `read`, `write`, and the bounded `finish` tool. Legacy aliases appear only with explicit CONTEXTOPUS_LEGACY_TOOLS=1 compatibility mode. First check actual host tool discovery, then the service tools/list and `guide(operation=...)` for one unknown signature. A source function or generated config does not prove model-visible access. Use MCP for workspace operations; direct internal calls bypass validation and observation.

Run `contextopus --version`, `contextopus service status` and `contextopus doctor` using the installed runtime. The application requires Python 3.12+. uv manages the application environment from a verified local wheel or GitHub release asset. Runtime and persistent storage are independent of plugin caches. An old cache remains a compatibility source for active old sessions, not the new runtime owner.

For actual missing requirements, report the observed failure, selected artifact/environment and expected network/disk scope. Reuse existing authorization and ask only for genuinely missing authority. Install only the agreed runtime or optional `local` extra with uv; do not change system Python protections, perform unrelated upgrades or download weights merely because a skill was invoked. After repair, repeat the failed check and verify the actual client MCP inventory. An import/version/health check does not prove inference or cached model availability.

## Local model and live connection

Model discovery follows the cheap base readiness check; it need not block dependency repair. Once tools are available, read the provider/profile through `status`. If tools are unavailable and the memory root is established, read only its known `<work-root>/core/rag/active.json` (legacy: `<work-root>/.pcw/.rag/active.json`) for `config.provider` and `config.profile`; old contexts may still have `<work-root>/.pcw/<workspace>/.pcw-runtime/active.json` before migration. Do not scan project sources or other roots. If no configuration exists, the bundled default is local `sentence-transformers` on CPU, `Qwen/Qwen3-Embedding-0.6B` revision `97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3`, `cache_folder: null`, and `local_files_only: false`.

The primary uses an existing `provider.cache_folder` and applicable cache environment settings, such as `SENTENCE_TRANSFORMERS_HOME`, `HF_HUB_CACHE`, or `HF_HOME`. With no overrides, the usual Hugging Face cache is under `~/.cache/huggingface/hub`. It inspects only the selected cache location without loading or downloading a model; cache inspection can wait until the base tools are available. Report known defaults/overrides and whether cached weights were actually established. If the final destination is not yet resolvable, say so rather than researching unrelated configuration or inventing a path.

Before an uncached load, disclose the model, known cache destination/defaults, weight download, storage, and CPU/RAM use; request any still-missing download permission. Do not invent a precise download size or latency measurement. Reuse existing permission and an existing verified cache. Read [Embedding configuration](procedure:reference/embeddings) when configuring offline loading or diagnosing a model failure. No remote embedding fallback is selected automatically.

The installed application owns one persistent local HTTP MCP service at `http://127.0.0.1:8765/mcp`. Inspect `contextopus service status`; start it only through an authorized explicit `contextopus service start` or initialization action. Native client configuration points to this shared endpoint. Avoid duplicate owner processes or one-shot runtime substitutes. After setup succeeds, use the host's supported reload/reconnect facility when available, then verify Contextopus tools are exposed and the pending operation succeeds. Health, dependency checks and an isolated MCP handshake do not establish the actual host connection.

If this host cannot reload its failed server, explain the remaining host-session restart requirement. Preserve the task and next action in the conversation and continue them after restart, without requiring the user to assign the task again. A separate process cannot reconnect the current host merely by starting successfully. Do not promise automatic reconnection or report memory saves/checkpoints that never occurred.

## Native service and client recovery

`contextopus service install` registers the per-user native OS service (systemd, LaunchAgent or Scheduled Task), enables login startup and starts the owner. Use `service start|stop|restart|status` or the main TUI controls. TUI start/stop is local and works without an MCP connection. Permission denial is not a stopped service. A running endpoint for another root must not be replaced implicitly.

After server readiness, `contextopus reconnect codex` attaches to the existing app-server proxy and queues `config/mcpServer/reload` for all loaded threads, not just Contextopus or one conversation. With `--thread ID`, it also verifies a real read through that thread. Never report a queued reload as a verified connection. OpenCode accepts `reconnect opencode --client-url URL --directory PROJECT` for an existing server, verifying its advertised API before disconnect/connect. Claude Code uses its native `/mcp` menu and Reconnect. Crush automatic renewal covers a previously established connection; failed initial connection has no verified external retry here. Resume the saved client session when a restart is required. See the installed-version evidence in the integration documentation.

## Bundled documentation and algorithm catalog

The explicit `core.init` operation (CLI `contextopus init`) prepares bundled documentation and the shared algorithm catalog after an active embedding profile is available. A first init without one reports `setup.status: model_setup_required`. Preview the model with `core.model_plan` and apply the exact authorized plan through `core.model_apply` (CLI `contextopus setupmodel --apply`). Successful model setup then installs the ordinary base documentation context and refreshes catalog vectors. Status, previews and searches never do these writes.

For an existing upgraded root, use an authorized init action to prepare current shipped documentation and algorithm catalog cards. Inspect its `setup.base_context` and `setup.algorithm_catalog` results. Conflicts preserve user-edited/deleted docs and include the exact incoming plan. If current rules require approval, show that plan and apply `core.base_install` with its `plan_revision` and actual `confirmation`; never fabricate confirmation. A pending delivery does not invalidate successful model setup. Retry the operation named by `next_action`, using the original plan revision for an interrupted base installation. Base selection is a separate documentation role and never changes the active task's rules.
