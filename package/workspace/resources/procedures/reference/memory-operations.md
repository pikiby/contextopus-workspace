# Memory operations

Mutating work operations require an active `cycle_id`. Search, reads, lists, instructions, the project record and history can be read independently without starting a cycle. Tools do not authenticate a human: invocation policy, chat presentation and any required approval are obligations of the cycle agent. Drafts and permanent changes are separate interfaces; no direct create/update/delete/link/restore MCP bypass is exposed.

## Temporary work

Temporary memory is optional. `tmp_write(cycle_id, content, ...)` stores a Markdown card under `.tmp`, with a readable filename and stable YAML ID. Shared assignments, reusable inputs, intermediate findings and handoff materials are useful cases; short replies and direct knowledge edits need no file. Use `tmp_list` for bounded descriptions, `tmp_read` for chosen cards, and `material_id`/`expected_revision` for updates. Ordinary and required links use the same mechanisms as knowledge. Temporary cards may reference other temporary cards or permanent knowledge; permanent records must not reference temporary data. Follow returned sources every time, even for temporary cards.

Store the exact user request with startup and relevant follow-ups through `clarification_add`. Keep interpretation separate. At each new task/cycle inspect `cycles_list` and needed existing cards; reuse matching work, update useful files, save verified durable facts and delete unneeded files through `tmp_delete`. That operation checks revisions, incoming links and the independent cleanup approval policy. Resolve dependencies before removal or a guarded rename. There is no mandatory per-file report status, review comment or disposition ledger. Native messages carry links between agents; the store does not schedule them. Temporary materials are not embedded, included in ordinary knowledge search or tracked by permanent Git history.

All permanent records, including tasks, goals and the project description, use `proposal_prepare/apply`, `read/read_many`, links and shared indexing. Set `type` and optional `status` in a change; type names are open vocabulary. Find relevant state through `search(types=[...], statuses=[...])` rather than remembering task IDs. Update only the selected context's records. Temporary material storage is optional; finish clears only the selected work after resolving its dependencies. Permanent YAML tags derive the owning context as context/<name>; other user tags are preserved and categories remain the search filter. INSTRUCTIONS is read in full and changed only through the [instructions procedure](procedure:instructions).

## Prepare a permanent change

The main agent or designated task lead, meaning the agent explicitly entrusted with leading the task in the same cycle, decides permanent-memory impact when accepting a substantive result as a basis for further work. Acceptance is the point when, after checking it, the agent is ready to rely on a self-contained conclusion at the next stage or in a handoff. Its own completed check, a reviewed worker return or an explicit user decision can reach that point; assess memory impact before moving to unrelated work or handing off, without waiting for the whole task to finish. Review the worker's evidence, scope and limits before treating its assertions as established. An individual tool call or report is not automatically an independently useful result.

At that point search by the accepted conclusion and read suitable existing topics. This comparison is separate from initial retrieval and is required even when no permanent write follows. Apply the complete instructions bound by the current Context.md for selection, organization and maintenance. Correct outdated or contradicted knowledge; retain supported, independently usable conclusions, the current task state or the user's decision/goal with its conditions. A user's choice establishes that decision or intention without requiring an empirical test of the choice; plans and goals do not establish successful outcomes. Preserve uncertainty and failed or outstanding checks. Unverified assertions and working-only details may remain in optional .tmp cards until they support a durable change.

Prepare, show and apply a ready change under the existing approval policy, then continue the same cycle. Repeat this acceptance and saving step as substantive results become ready rather than deferring all knowledge maintenance until completion. Keep mutually dependent record, status and link edits in one coherent proposal so that a narrowed conclusion and its task state remain consistent. Unrelated conclusions need not wait for one another or become one large final proposal. No mandatory temporary report or review ledger is introduced.

Before composing a permanent edit, reserve the existing affected cards together through `workspace.reserve(cycle_id, material_ids, reason)`. Give one short line explaining the actual edit. Read/search remain available. A busy response identifies the owning cycle, reason and expiry; continue independent work instead of bypassing the reservation. Reservations default to 15 minutes, can be renewed while live, and expire if a session disappears. `workspace.reservations` inspects them; `reservation_renew` extends an owned live reservation, and `reservation_release` releases its exact ID. After expiry/release, reread current cards, reserve again and reprepare; an old proposal cannot borrow a new reservation. Successful application releases its affected cards. No separate owner chat or new knowledge record is required.

Call `proposal_prepare(cycle_id, changes, replacements?, proposal_id?, no_changes_reason?, transformations?, summary?)`. It stores a plan and review in .tmp; it does not write permanent materials. Each change describes one final topic. Its title comes from the Markdown heading in content; do not send a separate title field. `guide(operation="workspace.proposal_prepare")` exposes the exact nested change schema when needed:

```json
[
  {"key": "new-topic", "content": "# Topic\n\nEstablished result, evidence and conditions.", "description": "Established result and the conditions for applying it.", "links": ["existing.md"]},
  {"material_id": "existing.md", "expected_revision": "revision-from-read", "content": "Revised complete body", "description": "Reviewed description of the revised subject and conditions.", "links": ["@new-topic"]}
]
```

- A new topic uses a unique `key`, complete `content` and author-written `description`; the plugin generates a stable YAML `id` and a descriptive filename from the heading. An explicit `path` relative to knowledge may choose the filename. `@key` refers to another new topic in this set, including mutual links. Duplicate IDs and destination paths are rejected.
- Required sources use a fenced YAML `sources` block inside `content`, with an unambiguous `reference` and bounded retrieval `instruction`. References are not limited to URLs: files, records, queries and knowledge fragments are supported by the agent's reading procedure. These are separate from navigation `links`. Apply INSTRUCTIONS authoring criteria; preserve blocks when revising/splitting relevant content and show their changes/removals. On receipt follow [required-source reading](procedure:reference/required-sources) regardless of authoring settings.
- An existing topic requires `material_id` and `expected_revision`. Supply changed `content`, complete outgoing `links`, a concise `description`, or a `path` relative to knowledge. Actual body changes require the reviewed description, which may equal the previous one; metadata-only edits preserve omitted fields. Renaming keeps the YAML ID and includes affected local incoming Obsidian links in review; a foreign incoming link requires explicit cross-context resolution before renaming. Metadata/path-only changes do not reembed. Link targets can belong to another context under the same memory root; returned labels include their workspace. Reading them does not change active rules. Writes affect the selected context; foreign incoming links must be explicitly corrected before deleting their target.
- Deletion uses `material_id`, `expected_revision`, `delete:true` without other changes on that entry.
- A merge supplies the final survivor plus deleted entries and `replacements: {"old.md": "survivor.md"}`. A split supplies the revised original and new topics. A replacement target may be `@key`. Declare `transformations: [{"kind": "merge", "sources": ["first.md", "second.md"], "targets": ["@combined"]}]`, or `kind: "split"` with one source and multiple targets. Include a retained source ID in targets. Supply a concise one-line `summary`. These provenance declarations enter the reviewed revision and Git commit, and must be shown with the changed passages. Follow [History and analytics](procedure:reference/history-analytics).
- Incoming link removal/redirection is computed before application and included in the review. The apply checks complete file fingerprints, including links and paths, so concurrent navigation changes also conflict.
- To revise an unapplied proposal, supply its `proposal_id`. The returned revision changes; earlier approval cannot apply the revised contents.

If comparison establishes that nothing needs changing, explain the conclusion without inventing a permanent update. Optional `changes: []` and `no_changes_reason` can record a no-change review, but are not prerequisites for finish. Actual proposals retain exact content, affected record and rule/settings revision checks. Unrelated temporary edits neither prove semantic review nor automatically invalidate it. Reinspect new evidence that changes the proposed conclusion.

The response contains the proposal ID/revision, created-ID map, review path, structural effects and `review_changes`. Each review entry identifies its topic and paths, contains exact before/after body passages with nearby context, and names added/removed link targets. Creates/deletions contain the complete added/removed body; unchanged bodies are omitted. Automatic incoming-link changes are included. `proposal_read` also returns these entries when retrieving a saved proposal; no extra read is needed immediately after preparation.

Present the actual changes in chat according to the complete active instruction documents: topic names, full new text or exact before/after passages, deletions, moves and link effects. A file link, UUID, tool log or general summary does not replace the changed content. Large proposals may span messages. Present the full scope in both approval modes; ask only when the workspace requires approval. The review file is supplementary.

## Apply under the workspace policy

If `material_max_tokens` is configured, preparation counts each final body with the index tokenizer. A `needs_split` response lists the exact oversized entries and counts, without writing knowledge or saving an applicable proposal. Revise semantic topics and prepare again; the limit never chooses the meaning boundaries for the agent.

`proposal_apply(cycle_id, proposal_id, expected_revision, confirmation?)` applies the previously shown version. The effective Core configuration value `knowledge_approval_required` selects the mode. With `true`, wait for approval of the shown revision and pass the actual user message as `confirmation`; silence, saved approvals and self-approval do not qualify. With `false`, apply after presenting the changes without waiting or supplying confirmation. Missing setting retains required approval for existing/custom instructions; malformed settings are errors. Creation supplies explicit machine values separately from the free-form rules. Preparation returns `approval_required` and the corresponding `next_action`. The policy is read from current effective machine settings, never chosen in apply arguments. Instruction edits follow the independent `instructions_approval_required` current effective machine setting (restrictive legacy absence means true), through the instructions procedure. A proposed change to false still requires approval under current true rules.

The plugin validates the full affected set before writing, writes survivors and incoming links before deletion, then indexes changed bodies. Links-only and unchanged-body updates do not reembed. A partial failure preserves tmp and the same proposal; retry that operation rather than generating duplicate materials. An already-started authorized application can finish recovery if instructions subsequently change; complete the work under the current instructions before closure. An external conflict requires reinspection, a new proposal, presentation and approval if the policy requires it. An already applied retry returns its receipt without writing again.

Successful application leaves the cycle active and temporary materials available for the next stage; several proposals can be saved within that same cycle. A prepared proposal awaiting approval is not saved knowledge. Keep it pending and continue independent authorized work when useful, without assuming its changes have been applied. If later evidence changes the proposal or overlapping records, reread and revise it, then show the new revision and obtain any required approval again. Report actual save, indexing and Git outcomes independently.

Discard an exact rejected/unneeded unapplied proposal with `proposal_discard`. Discard changes no permanent knowledge and leaves temporary evidence until closure. Do not label partial application as rejection or completion.

Preparation also reserves automatic incoming-link changes and newly allocated IDs as one set. For compatibility, callers without a prior reserve get a short reservation during preparation, using the proposal summary or a neutral operation label. This does not replace the procedure's explicit edit reason. Competing preparation cannot acquire part of a conflicting set. Application checks the exact reservation generation, current record versions and approval policy. Revision/discard releases dropped claims not shared with other pending proposals; completed/cancelled cycle cleanup releases only that cycle's claims. Ordinary pause does not close work; reservations eventually expire. Existing pre-upgrade proposals retain their reviewed bytes and acquire reservations at application after conflict checks. A partially applied operation can reacquire only after the original before/after verification passes.

Reservations protect Workspace mutation paths, including internal updates, moves, merges and migration. External editors can still change ordinary Markdown files; revision checks detect observed external changes, but advisory reservations do not provide filesystem isolation. Two newly created records about the same topic still require semantic duplicate checking. Independent sessions use independent cycles; workers deliberately sharing a cycle also share its reservation ownership.

## Close or restart

Use the dedicated MCP `finish` tool only when the bounded work is resolved. Recheck its remaining conclusions against current permanent knowledge and resolve any remaining changes before cleanup; earlier saves do not close the cycle or replace this final check. Read `workspace.status`: it provides exact temporary paths and `cleanup_revision`. Pass that revision as `expected_revision`; changed files require a new preview. The effective `cleanup_approval_required` controls actual user confirmation, independently of the other approval settings. With false, call without an extra permission question; with true, show the deletion scope and wait for its approval. Prepared proposals must be applied or discarded, applications/indexing completed, and incoming dependencies from other work resolved. No temporary report, folder-checksum proof of reasoning or mandatory no-change proposal is required.

Only the selected work is cleaned. Pause, handoff and unresolved useful work retain necessary materials. `cancel:true` requires actual user cancellation and never rolls back permanent knowledge. A rejected cleanup must not be retried through an indirect alias or shell deletion. A retry of an already completed finish is idempotent.

Before a new task inspect existing cycles. Continue matching work with the same ID only for an intentional continuation or handoff; independent sessions must not borrow another active cycle to bypass its reservations. Use a fresh request_id and exact user_request only for new authorized work; preserve clarifications verbatim. An explicit restart cannot discard outstanding files or proposals without the cleanup procedure. Cycle IDs are not native session IDs; a clean-context main agent can take over the same work.

## History and older workspaces

When enabled in effective machine settings, local Git captures permanent data automatically. `history_list/search/changes/diff/read` expose older versions and declared transformations; restoration is an ordinary shown proposal. `history_retry` uses immutable saved snapshots after a failed commit. Legacy manual `checkpoint` accepts only exact knowledge paths with separate user authority. Tmp, analytics and runtime state are excluded. See [History and analytics](procedure:reference/history-analytics).

Opening checks format without hidden migration or creation. On incompatibility immediately run upgrade, then resume. It preserves IDs, factual content, links and custom instructions while converting filename identity to YAML, legacy source syntax and the shared RAG. Legacy Current content and PROJECT are migrated into typed records, preserving IDs and pending proposals; semantic rewriting is separate requested work. Missing derived storage uses recovery or upgrade; missing knowledge remains blocked. Never create a replacement empty memory to bypass incompatibility.
