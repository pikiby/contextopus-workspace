# Create context

Use `read` for queries and `write` for changes under the ordinary [Workspace procedure](procedure:workspace). The names below are operations; place their parameters in `arguments`. Describe only an unknown signature.

1. Follow [context selection](procedure:workspace). Establish the actual creation request and project/task scope. Accept any clear natural-language description; do not require parameter names.
2. Choose a context name in the connected server. Use `workspace.contexts` to check existing names without startup; do not ask for a storage path. The server determines the folder and creates required directories. Never overwrite an existing context. Context names are unique using Unicode NFKC plus case-insensitive comparison; resolve a reported collision explicitly. Changing the server's storage location is a separate installation task, not context creation.
3. Read the packaged [default instructions](procedure:default-instructions): content is the free-form rules template; the separate creation_defaults object comes from canonical Core creation defaults. First offer those values as **one standard set**, in ordinary conversation language. The standard currently means: work updates require a Workspace invocation; shown record changes do not wait for additional approval; local Git history is on; each material is limited to 1024 tokens; automatic authoring of required-source links is off (existing required sources are still checked); constant instructions rereading is off; deletion of temporary work needs no extra approval under cleanup_approval_required=false. The user can enable cleanup approval when customizing or later through settings. Explain that instructions changes require approval under the independent `instructions_approval_required: true` default. Ask one question: **Use these settings (recommended)** or **Customize settings**. Preserve any settings the user already supplied and show those overrides in the offered set. A clear acceptance selects all displayed settings; silence or a preselected option does not. Do not ask again when all values are already unambiguously supplied.
   If the user declines the set or requests customization, ask **separate questions** only for unanswered settings: `allow_implicit_updates`, `knowledge_approval_required`, `instructions_approval_required`, `cleanup_approval_required`, `git_history_enabled`, `material_max_tokens`, `create_required_sources`, and `reread_instructions`. For instructions approval, offer **Yes (recommended)** and **No** separately from knowledge approval. For temporary cleanup approval, offer **No (recommended)** and **Yes**, independently of knowledge/instruction approval. For the size question, offer **1024 tokens (recommended)**, **Another limit**, **No limit**, in that order. Ask for a positive number only for another unspecified limit; no limit means null. For source links ask whether the agent should add references whose specified information must be freshly checked on every receipt. Do not infer this choice from general write permission. For rereading, offer **Only on a new task, context/rule change or lost text (recommended)** and **On every invocation**; an explicitly requested agent/model profile affects that rereading choice only. Wait for the actual answers; never treat refusal of the standard set as disabling all settings.
4. Compose the complete free-form INSTRUCTIONS from that one template. Keep the policy values and the selected rereading value in the separate settings object; do not write machine flags into INSTRUCTIONS. The standard rereading mode is false; explicit agent/model overrides never grant additional permissions. Compose the project record and its author-written project_description from the user's stated purpose, goals and boundaries. If source links are accepted, include the template's Required sources rule directing the agent to create them under its stated criteria. If declined, keep the setting false; no authoring obligation is enabled. Show the resulting instructions, project text, settings and context name so the agreed creation is concrete. Do not import unapproved facts from chat as knowledge.
5. Call `workspace_create(request_id, instructions_content, project_content, user_request, settings, project_description)` with the exact agreed texts, separate settings object, reviewed description and the user's creation request. Pass the agreed context name outside arguments. Retry identical input with the same request ID. Creation writes and indexes the initial project record, initializes no task and opens no cycle. Verify the returned context, settings and independent Git status.
6. If the user also authorized actual work, begin the [work cycle](procedure:workspace). Otherwise report creation and stop; an empty new context needs no fabricated knowledge, proposal or finish call. Keep the context name for continuation.


Canonical layout: the indexed project record lives at the context root as `Context.md` (`type: project`). Its YAML `instructions` mapping binds the complete shared rules in Core (`core/instructions`), including Workspace and optional Agents rules. Startup returns every required document in full; follow `reread_instructions` to reuse text already available for the same task. Existing roots move to this layout only through the explicit reviewed upgrade plan/apply path with retained backups.
